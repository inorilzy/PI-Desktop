输入区 · 数据流

数据怎么在宿主、输入框和插件之间流动：四个界面槽、读写草稿两个方法和附件三动作、记号的一生，以及发送时发生什么。每个接口写清传什么、返回什么、错误情况，配调用示例和示例场景。字段名是建议值，结构是拍板的。

status: draft · issue #545 · 对照 requirements.html 与 demo.html

1接口约定 已定

每个接口三件套：传什么 / 返回什么（含错误）、调用示例、示例场景（文字场景，不是界面演示）。字段名是建议值，结构是拍板的。

四个界面槽

槽插件拿到什么插件能做什么
composer.left所在会话、当前草稿文字在左排固定件（附件 / 模式 / 权限）右边加自己的按钮和弹层
composer.middle所在会话、当前草稿文字加自己的按钮；通过排序声明处置宿主现成组件 ContextUsage——可隐藏、可显示、可重排（契约见下）
composer.trigger用户打出符号后的筛选文字返回列表行和状态之一（见下面的形状）
composer.content触发符选中项的数据给出记号的 icon 和文字。记号外形宿主固定，【icon | 文字】（拍板）

中槽 composer.middle（拍板：排序权归插件；写法对齐 ui/user-message）

插件能拿到的数据

// 槽输入（宿主 → 插件）
{
  sessionId,
  draftText                    // 当前草稿文字。用量数据不随槽给——组件自己有
}

宿主提供的现成组件（插件可以直接用，也可以不用、自己画；不是必须套的外壳）

组件画什么不用它的话，插件要自己做什么
ContextUsage上下文用量：圆环 + 百分比，点开有明细弹层。数据、交互、样子都是组件自带的，默认装在中槽里用量显示和明细弹层全部自己画；数据可以找宿主要（usedTokens / maxTokens / percent / cacheHitPercent，字段名是建议值）

插件交回的：一次排序声明

{
  order: [ "ContextUsage", "self.polish", "self.undo" ]
  // ContextUsage = 宿主的现成组件，写在哪它就排在哪
  // self.*       = 本插件的按钮，按数组顺序排
  // 不写进数组 = 隐藏。不写 ContextUsage 就是把它藏掉，
  // 再画自己的等效显示，就是「替换」（demo 场景 4）
}
多个插件怎么合成一个中槽。插件之间按声明（安装）顺序依次展开各自的 order 数组；对 ContextUsage 的处置以声明顺序第一个表态的插件为准，后面的插件再声明无效——和触发符「先装者为准」同一个思路。插件出错或卸载时，按剩余插件的声明顺序重算；没人表态，ContextUsage 回默认位置。

不提供什么

不给为什么
ContextUsage 的内部样子组件长什么样、点开弹层里有什么，是宿主的；插件只能决定摆不摆、摆在哪，不能改它的内部
中槽里的其他宿主控件中槽里宿主的东西只有 ContextUsage 一个；模型选择、发送 / 停止不在中槽范围
草稿与附件中槽只管这一段按钮的摆法；读写草稿和附件走三个方法，不挂在槽上

示例场景：草稿统计插件在默认顺序里加一个自己的按钮（demo 场景 7），或把 ContextUsage 排到自己按钮后面（demo 场景 8）；用量增强插件把 ContextUsage 藏掉，换成自己画的更细用量（demo 场景 4）。

方法 ① 读草稿（权限 composer.readDraft）

// 请求：无参数
composer.readDraft()

// 返回
{
  sessionId,                // 当前会话 id；没有会话时整次调用报错
  version,                  // 草稿版本号；每次草稿变化后 +1（用户打字、删改、插件写入都算），按会话计
  text,                     // 输入框当前文字，每个记号占一个内部字符
  tokens: [                 // 记号列表，按在 text 里出现的顺序
    { key, label, send, payload, at }
    // key = 宿主登记记号时分配的稳定 id，全程不变
    // at  = 记号内部字符在 text 里的位置，仅用于展示 / 统计
    // payload 只还给写入它的那个插件；别家记号此字段省略
  ]
}

示例场景：草稿统计插件（demo 场景 7）每次草稿变化后读一次，算出字数和 token 估算画在自己按钮上；增强类插件把快照原样存下来，供自己的撤销用。

方法 ② 写草稿（权限 composer.writeDraft）

// 请求
composer.writeDraft({
  sessionId,               // 必须是 read 时的会话；对不上当前会话整次拒绝
  baseVersion,               // 之前 readDraft 拿到的版本号；提交时刻比对，先到先得
  text,                      // 可混排三种内容：普通文字、{{t1}} 新记号占位符、
                             // read 给过的内部字符（记号引用，原样放回即可）
  tokens: [                  // 两种形态
    { key },                               // 引用：既有记号，宿主用登记表里的原 label / send / payload
    { key: "t1", label, send, payload }   // 新记号：对应 text 里的 {{t1}}，宿主分配内部字符和正式 key
  ],
  mode: "replace" | "insert"   // 整体替换 / 光标处插入
})

// 返回
{ version }                  // 写入后的新版本号
  • replace 是「所见即所写」：新 text 里没有出现的既有记号就是被删了；要保住（自己的、别人的、用户的 @文件）就把它作为引用放进 tokens，内部字符原样留在 text 里。
  • 引用的 key 不在登记表里 → 整次拒绝。insert 的 text 只允许普通文字和 {{t1}} 新记号，不接受引用。
  • 占位符只在本次请求的 tokens 里解析；正文里其他 {{…}} 按普通文字保留——想要字面的 {{t1}} 文字，就不要在 tokens 里声明 t1（不提供转义语法）。text 里出现某个占位符但 tokens 没给对应数据 → 整次拒绝。
  • 宿主分配内部字符和正式 key。登记表按会话只增不删（内存，重开应用即清）：草稿里的记号可以删，登记表留着，被删的记号凭 key 引用还能还原（撤销依赖这一点）。插件写入里的 {{t1}} 只是本次的临时名。
  • 版本号在每次草稿变化后 +1：用户打字、删改、插件写入都算。baseVersion 比对发生在宿主提交的那一刻，单线程先到先得，后到整次拒绝——不会静默覆盖别人的写入或用户刚打的字。
  • text 里的内部字符只认当前会话登记表里的，对不上 → 整次拒绝（防旧快照串会话）。
  • 宿主自己的记号（编辑锚点）插件动不了：replace 的 text 里丢掉它 → 整次拒绝，也不能引用它。
  • 写入必须在约 0.5 秒内被输入框真正显示，否则整次作废并报错。

示例场景：常用语插件（demo 场景 5）用 insert 在光标处插一段模板；润色插件（demo 场景 4）用 replace 换成润色后的整段文字，把用户原有的 @文件 记号作为引用带回去；撤销时重新 read 拿新 baseVersion，把旧快照原样回写。

附件三动作（一个权限 composer.attachments）

// ③ 加 —— 内容由插件自己存（存哪里由插件开发者决定），宿主只登记一条
composer.attachments.add({
  name: "chart.png",        // 显示名，必须带扩展名
  mimeType: "image/png",     // 决定画图片缩略还是文件芯片
  ref                        // 插件侧的地址（本地路径或 URL），指向内容本体
})
// 返回
{ id }                        // 登记成功才有 id，移除和记号引用都要用
// 错误：名字没有扩展名 → 整次拒绝

// ④ 列 —— 当前输入框里的全部附件
composer.attachments.list()
// 返回
[{ id, name, kind: "image" | "file", mimeType, size,
   source: "user" | 插件名 }]   // source 标记谁加的

// ⑤ 移
composer.attachments.remove(id)
// 返回
{ ok: true }
// 错误：id 不存在，或那条不是本插件加的（用户加的、别的插件加的）→ 拒绝，列表不变
插件附件的存法（拍板）。内容确实是插件生成的，但存在插件自己决定的地方，插件拿到地址后只把地址登记进附件区。宿主不存内容、没有暂存副本；发送时宿主按地址把内容取回来，当正常附件随消息发送，地址取不到 → 阻断这次发送并报错。大小上限在发送取内容时校验。内容本体的生命周期由插件自己管。附件登记随会话走：切会话即清空，随会话删除。

示例场景：图表插件生成 chart.png 存到自己管理的目录，add 登记地址拿到 id，list 把当前附件画进左槽按钮的弹层给用户看（demo 场景 6）；清理时只能 remove 自己加的那条登记。

触发符：注册与回答

// 清单里声明：一个触发符号（单个字符）。/ 和 @ 不开放；
// 安装时查冲突，先装者为准，后装者该符号不生效
{ "composer.trigger": "#" }

// 宿主 → 插件：用户打出符号后，每次筛选变化传一次
{ symbol: "#", query: "数据" }   // query 为空串 = 刚打出符号，还没输入

// 插件 → 宿主：四态回答，每次问询答一次
{ state: "loading" }
{ state: "ready", items: [
    { icon, title, description, hint,
      token: { label, send, payload } }   // 选中就用它，不再问第二次
] }
{ state: "empty", hint }
{ state: "error", message, retry }   // retry = 是否给重试按钮
  • 符号后面的文字是筛选条件；文字里出现空白，弹层关闭。
  • 弹层的外观、键盘交互是宿主的；四态回答协议与各状态样式、输入防抖均已按建议值拍板。

示例场景：数据源插件（demo 场景 3）收到 query 后去远程拉匹配项，先答 loading、拉到答 ready；失败答 error 并带重试按钮。

记号（chip）：插件一次给三样

{
  label: "知识库1",                    // 给人看，画在 chip 上，宿主不解析
  send:                                   // 给 AI，发送时替换记号所在位置
    { mode: "text", text: "#datadb:type2:id:1" }   // 展开成文字插回原位
  | { mode: "attachment", id }           // 变成结构化附件，引用本插件登记的那个（别家的 id 拒绝）
  | { mode: "none" }                      // 不发送，只是输入框里的元信息（编辑锚点用）
  payload: { … }                          // 插件自己的数据，宿主原样存、原样还，永不解析
}

示例场景：知识库引用。用户在触发符列表里选中「产品手册」，插件交 label: "产品手册"、send.text: "#datadb:type2:id:1"、payload: { kbId, docId }；发送时宿主把文字插回记号位置，payload 从不进消息。

key 由宿主分配（拍板）。插件交的只有 label / send / payload；宿主登记记号时分配内部字符和稳定 key（触发符选中的记号同样有），readDraft 返回的就是它。插件写入里的 {{名字}} 只是本次写入的临时名。
记号外形宿主固定（拍板）。样子是【icon | 文字】：icon 用选中列表项时的图标，文字是 label。插件不能换外形，和 @文件 引用一致。记号随历史消息持久化的契约对齐斜杠命令的存法，实现排在最后；之前编辑旧消息看到的是展开后的文字。

记号的一生

  1. 选中 — 插件交回 label、send、payload。宿主分配内部字符，把记号画进输入框，登记进记号表。
  2. 存在草稿里 — 记号表跟草稿存在同样的地方：内存，随会话切换保留，重开应用即清空。不落盘。
  3. 读出来 — readDraft 把文字和记号表一起交回，payload 原样还原。
  4. 发送 — 宿主机械展开，不问插件：text 的把文字插回原位；attachment 的让那个附件随消息走（同一附件不会发两份）；none 的直接消失。消息里存的是展开后的文字。

插件附件的一生

  1. 生成并自存 — 插件生成内容，存到自己决定的位置（自己的数据目录、服务端……），拿到一个地址。
  2. 登记 — attachments.add 交 { name, mimeType, ref }；宿主登记一条、画缩略，返回 id。宿主不存内容。
  3. 引用或发送 — 记号的 send.attachment 用 id 引用它；或用户直接带着它发送。发送时宿主按地址取回内容，当正常附件随消息走。
  4. 清理 — 内容本体由插件自己管；宿主侧只有登记条目，随附件区的移除而消失。

编辑历史消息

  1. 点「编辑」 — 正文回填到底部输入框，前面出现一个宿主自己的锚点记号（原文预览，超长隐藏；和 @文件 引用同一套机制）。原消息里的记号还原成 chip。
  2. 删锚点 — 退出编辑，剩下的文字变回一条普通新消息。
  3. 再点另一条的「编辑」 — 直接清空输入框、回填新的，未发送的改动直接丢弃（拍板：不保护）。
  4. 发送 — 走普通发送逻辑。有锚点时先删掉被编辑那条及之后的对话，再把编辑后的内容作为那条消息重发（拍板：截断重跑）。
手打的 #知识库1 不是记号。只有触发符选中、或插件通过占位符写入产生的才算。按文字样式反推记号要处理歧义和输入法，不做。

3出错怎么办 一定会遇到

情况结果靠什么保证
插件界面抛错只有出错的那一小块收起来，宿主把这个位置上自己的控件按默认布局画回来；其余插件不受影响每个位置独立的出错隔离
排序声明有问题整份声明作废，中槽按宿主默认布局画回order 里只能引用 ContextUsage 和本插件自己的按钮
列表拉取失败插件答 error 状态和文案，宿主用固定样式画出来；重试按钮由插件决定四态回答里的 error
写草稿超时整次写入作废，给插件一个明确的错误写入必须在约 0.5 秒内被输入框消费
插件自己做撤销可行：旧快照原样回写（既有记号按 key 引用带上），写回前重新读一次拿新版本号每次写入推进版本号；baseVersion 对不上整次拒绝
附件地址取不到 / 超限 / 登记已被移除阻断这次发送并报错；登记条目保留，移除后可重试发送时统一校验：地址可达、大小上限、id 还在附件区
移除别人的附件拒绝，输入框内容不变remove 只能动自己加的（source 校验）
插件被卸载位置收回，宿主控件画回来；草稿里残留的插件记号退化成普通文字，显示 label（txt）锚点记号是宿主的，不受影响
