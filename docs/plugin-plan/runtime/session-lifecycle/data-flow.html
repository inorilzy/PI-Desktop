session-lifecycle · 数据流

会话一生的五类通知从哪来、带什么、能不能拦。六节固定：接口约定 / 数据怎么走 / 出错怎么办 / 不提供什么 / 相关条目 / 还没定的事。

status: draft · issue #561 · 字段名是建议值

1接口约定 建议

headless 事件监听，runtime.session.lifecycle。除 before_compact 外全部 fire-and-forget。

// 插件 headless（建议形态）
pi.on("session_deleted", ({ sessionId }) => myCache.drop(sessionId))
pi.on("session_before_compact", ({ messages, tokensBefore, retained }) => {
  if (myIndex.pending(sessionId)) return { cancel: true }
  // 唯一能拦的时刻：压缩前
})

五类时刻

事件载荷可否决
created / deleted会话标识与元信息否
before_switch旧 / 新会话 id否
before_fork源会话与 fork 目标否
before_compact{ messages, messageCount, tokensBefore, retained }是（{ cancel: true }，30s 预算内）
compact / compact_failed结果否
权限runtime.session.lifecycle

3出错怎么办 已核实

情况结果靠什么保证
通知事件插件超时 / 抛错无人等待，流程照常fire-and-forget
before_compact 超时按不取消处理，压缩继续30s 预算
cancel 后插件长期不放手现状无计数；连续取消待拍板预算（限速待议）
无权限permission_denied槽权限门控

4不提供什么 已核实

不给为什么
切 / fork / 删的否决权用户直接操作，插件只旁观
原生 Pi 会话事件桌面不经手的路径（现状边界）
会话内容的写权只通知，不代管
无限拖延压缩cancel 在 30s 预算内；连续取消待限
